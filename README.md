# Agent Hub

פיילוט מקומי שמחבר את Codex ו-Claude Code ללוח משימות ולשיחות לקוח. כל הסוכנים, הנתונים ומצב העבודה מנוהלים ממקום אחד.

## הפעלה

חלץ את ה-ZIP לתיקיית עבודה והפעל מתוך `agent-hub` עם Python 3.10 ומעלה.

```sh
python3 hub.py
```

פתח את [הלוח המקומי](http://127.0.0.1:8765). הנתונים נשמרים ב-`hub.sqlite3` ליד הקוד. בהחלפת גרסה שמור את קובץ ה-SQLite. הממשק תומך במוצרים שכבר נוצרו. אפשר לבחור מסד נתונים ופורט אחרים עם `AGENT_HUB_DB` ו-`AGENT_HUB_PORT`.

כדי לשלוח הודעות ולהריץ סוכנים התקן את `codex` ו-`claude` והגדר אימות נתמך עבור הרצה לא אינטראקטיבית לפי התיעוד של הספקים. שמור את פרטי האימות בסביבת ההרצה של הספק, והפעל במפורש את המחברים.

```sh
AGENT_HUB_ENABLE_AGENTS=1 python3 hub.py
```

במוצר שבו מפתחים אמורים לערוך קבצים, הזן נתיב מוחלט ל-checkout מקומי של מאגר Git שאתה סומך עליו. הענף מתחיל מה-HEAD המקומי. עבודת כל מפתח נשמרת ב-worktree נפרד, בתיקיית `hub-worktrees` ליד מסד הנתונים. הקוד נשאר שם לסקירה ולבדיקות. הגישה היא למפעיל מקומי יחיד. להרצה משותפת נדרשים אימות משתמשים, הרשאות והרצת קוד בבידוד מתאים.

## מבט לקוח

פתח מנהל מוצר למוצר כולו או ללקוח מסוים. בחר ״מבט לקוח״ ופתח שיחה למוצר, ללקוח ולמנהל. הודעות נכנסות לתור והתשובה מ-Codex חוזרת לאותה שיחה. מנהל מוצר יכול לנהל שיחות נפרדות עם לקוחות שונים לפי תחום אחריותו. היסטוריית כל השיחות נשמרת מקומית. בכל פנייה נשלח לסוכן חלון של עד 16 הודעות אחרונות מאותה שיחה.

כשהדרישה בשלה, העבר אותה מהשיחה ללוח כמשימה מקושרת. השאר את ניסוח הדרישה וקריטריוני הקבלה פתוחים לעריכה לפני השליחה.

## מבט מנכ״ל

פתח את המוצר והגדר יעדים, הקשר, קול לקוחות, מאגר ותקציב. לכל מוצר בעלי תחום וכללים משלו. ב״כללי המוצר״ הארכיטקט ומעצב המוצר מובילים את גיבוש הכללים בעזרת מנהל המוצר והלקוחות או נציגם. אפשר להריץ חבילה ייעודית ל-Codex, לתעד הצעה ולהכניס נוסח סופי לתוקף לאחר תיעוד עמדת מנהל המוצר ומשוב הלקוחות. הטיוטות נשמרות לצד הגרסה שבתוקף. גרסה חדשה נכנסת לחבילות העבודה הבאות.

בעת הפעלת המחברים, דרישה שסווגה כממשק נכנסת לאפיון עיצובי ומזמנת מעצב. המעצב מציע זרימות, מסכים, מצבים וקריטריוני קבלה לפי דרישת הלקוח וכללי המוצר. לאחר שהמפעיל מאשר את האפיון בלוח, הארכיטקט מקבל אותו עם הדרישה. משימת תשתית עוברת ישירות לארכיטקט. שמירת תוכנית מזמנת את מנהל הפיתוח, שיבוץ משימה מזמן מפתח Claude, הגשת PR לסקירה מזמנת QA ובמשימת ממשק גם מעצב, בהרצה נפרדת שבודקת את המימוש מול האפיון והגרסה שהוגשה. יצירת מועמד לגרסה מזמנת QA לגרסה. את כל ההרצות ותוצריהן אפשר לראות בלוח. אפשר גם להריץ סוכן מתוך חבילת עבודה. אישור תוכנית, שיבוץ, תיעוד תוצאת בדיקה, מיזוג ואישור גרסה מבוצעים בלוח על ידי המפעיל. הלוח אוכף תלויות, עדיפויות ומכסת עבודות פעילות לפני שיבוץ. כישלון סקירה שנרשם בלוח פותח באג מקושר.

התור מעדכן שימוש לפי הנתונים שהספקים מחזירים. ספי הטוקנים והעלות חוסמים התחלת ריצות חדשות לאחר שהשימוש שנרשם הגיע לסף. ריצות מקבילות יכולות להשלים מעבר לסף. Codex מדווח טוקנים דרך המתאם והחיוב שלו ניתן להשלמה ידנית. ל-Claude נקבעת גם מסגרת עלות משוערת לריצה, עד `AGENT_HUB_CLAUDE_RUN_USD` (ברירת מחדל $2) או יתרת תקציב המוצר שנרשמה בתחילת הריצה, לפי הנמוך.

## מה נדרש לחיבור למאגר ולסביבת בדיקות

כאן האירועים מגיעים מפעולות בלוח. האינטגרציה עם GitHub Webhooks, CI והרצת דפדפן על Preview טרם חוברה. הסקירה האוטומטית היא ניתוח ההקשר והראיות שנמסרו לסוכן. כדי לאשר QA או סקירת עיצוב, צרף תוצאות בדיקות ותצוגה מהגרסה הנכונה. את ה-PR, המיזוג והפריסה מפעילים בכלי המוצר. הגנות הענפים ב-GitHub יכולות לאכוף את הדרישות גם מחוץ ללוח.

- [Codex בהרצה לא אינטראקטיבית](https://learn.chatgpt.com/docs/non-interactive-mode)
- [Claude Code CLI](https://code.claude.com/docs/en/cli-reference)
- [הגנת ענפים ב-GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)

## ניהול תוכן ותור מימוש

בהגדרות מוצר אפשר להפעיל את מנהל התוכן ב-Codex, לבחור איפה התוכן נשמר ולתעד סכימה, שדות, כללי עריכה ודרך הזנה. מנהל המוצר מעביר משימות מתאימות לתור התוכן מהלוח או משיחת לקוח. התור שומר את מקור המשימה ואת העדיפות. הרצת תוכן אחת בכל פעם מתבצעת לכל מוצר, לפי סדר העדיפות. תור הפיתוח מציג את משימות התשתית והממשק בנפרד.

- **CMS, מסד נתונים או API נפרד**. מנהל התוכן עובד ישירות מול מנהל המוצר. הסוכן מכין תוכן לפי הכללים הקיימים. המפעיל מתעד את הטיוטה, הזנה במערכת התוכן ואסמכתה לפרסום. חיבור כתיבה אוטומטי ל-CMS או ל-API דורש מתאם למוצר הספציפי.
- **תוכן במאגר Git**. מנהל המוצר יוזם את המשימה. הארכיטקט מגדיר את תיקיית התוכן ואת הבדיקות, מנהל הפיתוח משבץ, ומנהל התוכן עובד ב-worktree ייעודי. תוצאת ההרצה מסומנת ככישלון אם שינויים התגלו מחוץ לתיקיית התוכן או אם ה-HEAD השתנה. בודק חייב לאשר את ה-commit שהוגש לפני תיעוד המיזוג. פתיחת ה-PR והמיזוג מתבצעים בכלי Git של המוצר.
- **שינוי סכימה או יכולת חדשה**. פותחים משימת תשתית נפרדת לארכיטקט ולמנהל הפיתוח. הארכיטקט מגדיר את החוזה בין התשתית לתוכן. לדוגמה, ב-Wordflow סוג שאלה חדש הוא שינוי תשתית. שיעור חדש המשתמש בסוגי שאלות קיימים הוא משימת תוכן.

## קליטת פרויקט קיים

1. פתח מוצר, הזן את נתיב ה-checkout המקומי, ופתח מנהל מוצר שאחראי למוצר כולו.
2. בחר ״קלוט פרויקט קיים״ והדבק את שיחת המימוש או קטעים רלוונטיים. הטקסט נשמר ב-Agent Hub. מזהה ה-commit הנוכחי ננעל כבסיס לסקירה.
3. מנהל המוצר מעבד את השיחה לתקציר מוצר. בדוק ואשר את התקציר. רק אז הסקירות של הארכיטקט והמעצב נכנסות לתור. הן מקבלות את התקציר המאושר ואת קוד המקור של ה-commit שנקבע, ללא קבצים מקומיים שטרם נכנסו ל-Git. המעצב מסמן מה נדרש לאמת בתצוגה חיה. אם המחברים כבויים, המפעיל יכול להזין סקירות שהוכנו בנפרד.
4. אשר את בסיס הארכיטקטורה, כללי העיצוב ורשימת השינויים המוצעים. ההמלצות נשמרות לעיון. כדי לממש אותן פותחים משימות, ולאחר אישור הקליטה אפשר לשבץ עבודה בלוח. הקליטה עצמה מבצעת סקירה ושומרת החלטות, ומאגר המקור משמש לקריאה.

ייבוא שיחה אוטומטי וקישור למאגר GitHub דרך האתר הם חלק מחיבור הענן העתידי. הפיילוט המקומי מקבל טקסט מודבק ו-checkout שכבר קיים על המחשב שמריץ אותו.

## צוות פיתוח משותף

במבט המנכ״ל, ״תור הפיתוח המשותף״ מציג עבודה פעילה, עבודה זמינה לשיבוץ, משימות שממתינות לתלות או לקליטה ומשימות בסקירה מכל המוצרים. אפשר לשבץ ישירות מהתור. חבילת מנהל הפיתוח כוללת את אותו מבט רוחבי, עם תקציבים וגרסאות של כל מוצר. חבילות המפתחים והבודקים נשארות ממוקדות במוצר ובמשימה שלהם.

ב״יעדי מנכ״ל וקיבולת צוות״ קובעים תקרה אחת לכל המוצרים יחד, עם ברירת מחדל של שני מקומות. היא נאכפת לצד התקרה של כל מוצר. מפתח אחד יכול להחזיק משימה פעילה אחת בין המוצרים. משימת תוכן במאגר Git צורכת מקום בזמן השיבוץ למימוש תחת מנהל הפיתוח. תוכן חיצוני נשאר בתור התוכן הנפרד. מעבר לסקירה משחרר את המקום לשיבוץ חדש. מנהל הפיתוח מציע חלוקת קיבולת ועדיפויות. המפעיל רושם את השיבוץ בלוח.

## מסמכי החברה ותיאום בין המוצרים

במבט המנכ״ל אפשר למנות מנהל עיצוב ראשי, ארכיטקט ראשי ומנהל מוצר ראשי. הם מנהלים את ההנחיות המשותפות בתחום שלהם. בעל תפקיד במוצר יכול להעלות שינוי ממוצר נבחר. אם חיבור הסוכנים פעיל, ההצעה מפעילה אוטומטית את מנהל התחום ב-Codex. הוא מקבל את הגרסה הנוכחית, כללים מקומיים וחריגים בתחום, ובודק השפעה על המוצרים. לאחר סקירה, ההתייעצות עם בעלי התפקידים ותוצאותיה נרשמות בלוח, והמפעיל מפרסם נוסח מלא ותקציר שינויים.

לכל מסמך יש היסטוריית גרסאות. מוצרים קיימים מאמצים גרסה במפורש עם חריגים מאושרים. מוצר חדש מתחיל בגרסאות העדכניות בעת פתיחתו. הלוח מציג אילו מוצרים טרם אימצו. סוכני המוצרים מקבלים את הגרסה שאומצה לצד כללי המוצר. התהליך מופעל מהצעות שנכנסות ללוח. שיחות התיאום עצמן ותזכורות תקופתיות אינן מופעלות אוטומטית בפיילוט.

### ערכת העיצוב המשותפת

פרסום גרסת עיצוב של החברה כולל הפניות לגרסאות של הנכסים לשימוש חוזר, כגון טיפוגרפיה, אייקונים, כפתורים, כרטיסים ודוגמאות למוצרים לילדים ולמבוגרים. אפשר לרשום קישורים או נתיבי מאגר עם תג או commit. מנהל העיצוב הראשי מתחזק את ההפניות יחד עם ההנחיות. מוצר שאימץ גרסה מעביר את ההפניות שלה בחבילות העבודה לצד החריגים המקומיים. הערכה עצמה נשמרת בכלי העיצוב או במאגר הרכיבים של החברה.

### סקירת מסקנות לפי אירועים

כשמנהלי מוצר מעבירים דרישה ללוח, או כשנרשמים אפיון עיצובי, תוכנית ארכיטקטורה, סקירת עיצוב, הצעת כללים או מסקנת קליטה, המסקנה נרשמת בתיבת מנהל התחום הראשי. גם תוצרי סוכן של הארכיטקט או המעצב במשימות מועברים לתיבה. אפשר להעביר מסקנה נוספת ידנית. שיחות הלקוח נשארות בשיחה, ודרישה שהועברה מתועדת בלוח.

אם מנהל התחום מונה והמחברים פעילים, הסקירה מופעלת בזמן ההעברה. היא משווה למסמכי החברה, למסקנות אחרות ולחריגים לפי מוצר ומציעה אישור או תיקון. המפעיל מתעד את ההמלצה בלוח, והיא מופיעה במשימה המקושרת ובחבילות העבודה הרלוונטיות. המלצה היא תוצר לדיון. כדי לשנות סטנדרט חברה מפרסמים גרסה במסלול מסמכי החברה.

## פריסה ראשונה ל-GitHub Pages

גרסת Pages היא לוח לניהול מהטלפון. היא שומרת מוצרים, משימות, שיחות שנפתחו, כללים והחלטות בכספת מוצפנת בדפדפן בעזרת משפט סיסמה. הנתונים אינם חלק מהמאגר או מתוצר הבנייה. אין סנכרון בין מכשירים, שחזור סיסמה או גיבוי מובנה בשלב זה. נתונים שנשמרו בהרצה המקומית אינם עוברים אוטומטית לגרסת Pages. הכתובת הסטטית יכולה להיות ציבורית. הצפנת הנתונים בדפדפן אינה הופכת את האתר לאתר ארגוני עם התחברות שרת והרשאות משתמשים.

הגרסה כוללת את לוחות החברה והמוצר, קישורים למאגר, לאתר החי, לסביבת בדיקות ולקישורים נוספים, סטטוס מוצר, משימות וגרסאות, וחבילות עבודה ידניות. להרצת סוכנים, ניהול PRs אוטומטי ושיתוף נתונים נדרש חיבור שרת. סטטוס הפרויקט מוזן בלוח והסטטוסים של משימות וגרסאות נגזרים מנתוני הלוח. סטטוסים של ריצות GitHub חיצוניות זמינים דרך הקישור ל-Actions של הפרויקט.

1. העלה את תכולת תיקיית `agent-hub` למאגר GitHub ייעודי. תבנית הפריסה נמצאת ב-`.github/workflows/deploy.yml`. מאגר ונתוני מוצר קיימים נשארים במקומם.
2. במאגר הניהול בחר Settings → Pages → Source → GitHub Actions.
3. דחף ל-`main` או הרץ את ״Deploy Agent Hub to GitHub Pages״ ידנית. הבנייה מריצה בדיקות ומפרסמת רק את `dist`.
4. פתח את הכתובת שמופיעה ב-Settings → Pages. בהפעלה ראשונה בחר סיסמה באורך 6 תווים לפחות, בלי דרישה לסוג תווים מסוים. אל תכניס אותו למאגר.

לבדיקה מקומית של הבנייה, הרץ `npm ci --ignore-scripts`, אחר כך `npm test` ו-`npm run build`.

- [GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/what-is-github-pages)

### אשף תשתית לפרויקט

כל יצירת פרויקט נפתחת באשף. בוחרים מאגר חדש או קיים, מגדירים ענף בסיס ושירות פריסה, ובוחרים בין אחסון בדפדפן, אתר ללא מסד נתונים, Cloudflare D1 או מסד אחר. אפשר לסמן מה כבר הוקם ולשמור גם כששלבים עדיין ממתינים. האשף מדריך להגדרות הרלוונטיות, והבחירות מוצגות בכרטיס הפרויקט. כדי להשלים או לעדכן פרטים, פתח שוב את ״אשף תשתית הפרויקט״ מתוך הכרטיס.

האשף שומר תיעוד. יצירת הריפו, הגדרת Pages או שירות אחר, והקמת מסד נתונים נעשות אצל הספק הנבחר. גרסת Agent Hub שמארחים ב-GitHub Pages שומרת את נתוני הלוח בדפדפן. מסד נתונים של מוצר שמוגדר באשף מיועד למוצר הזה, והגדרתו אינה מעבירה אליו את נתוני לוח המנכ״ל.
